# Local service recovery — 13 October 2026

## Findings

- Docker records validator1 as OOMKilled, exit 137, on 17 September at 08:09:45 UTC. It had no container memory limit or restart policy. The surviving three validators agreed on finalized block 39543 during the initial inspection.
- The portal used validator1 exclusively; the publisher therefore reported Ledger unavailable. Ledger redundancy did not provide application endpoint failover.
- Docker Desktop has about 7.75 GiB available to all containers. Before recovery the portal used 1.10 GiB, six workers about 1.16 GiB combined, and ClamAV about 1 GiB. Historical memory time series and the kernel OOM selection log are unavailable; a memory leak has not been established.
- A complete snapshot was 2,098,769 bytes, containing 598 rounds and 1,447 observations, taking about 611 ms to retrieve in one diagnostic. Workers poll every two seconds; event inclusion checks also retrieve full snapshots every second. These are plausible allocation/load amplifiers, not proof of the OOM root cause.
- ClamAV was actually functioning with current signatures. The image health check used localhost, resolving to ::1, whereas the configured listener uses IPv4. Direct IPv4 PING returned PONG. Signature database 28151 was dated 12 October.

## Recovery performed

Collection and the portal were stopped briefly to release memory. Validator1 restarted from its existing chain and signing databases without a reset, restore or key change, and began replaying missed blocks. While it catches up, the portal uses validator2 via the ignored `deploy/pilot-runtime/recovery.override.yaml`. Workers and publisher were recreated against the portal's new network namespace.

The checked-in Compose scanner health check now explicitly probes 127.0.0.1:3310 with a timeout. The scanner reports healthy and a harmless streamed scan completed successfully. Signature data was retained.

The temporary deployment uses both Compose files:

```sh
docker compose -f deploy/compose.pilot.yaml -f deploy/pilot-runtime/recovery.override.yaml --profile mining-test --profile bulk-test up -d
```

Do not silently redeploy with only the base file while validator1 is still behind: that would point the portal back at the recovering node. No automatic RPC failover has been implemented by this recovery.

## Remaining release gates

Measure peak and trend memory under sustained collection, profile growing allocations if present, reduce redundant snapshot work, and set tested resource budgets. Automatic restart and endpoint failover are separate hardening work. Validator1 must finish replay and agree on a current finalized block before calling the four-node recovery complete. Recheck contributor availability and new observations after restart; process liveness alone is insufficient.

## Live validation

The restored API reported healthy advancing finality. Four contributors renewed signed availability at heights 39563–39568, and the publisher opened a new Stack Overflow collection round at height 39569 (599 rounds total, up from 598). This confirms work scheduling resumed; the new round was still pending at this check, so completed verification is not claimed. After collection resumed, the portal used about 455 MiB; total observed container usage was about 4.7 GiB of Docker’s 7.75 GiB allocation. These are point-in-time readings, not a long-term memory test.
